## 前回のおさらい

[前回](/ja/blog/docker-build)は、EmDash を公式の `Dockerfile` からビルドして、こう起こしました。

```console
❯ docker volume create emdash-data
emdash-data
❯ docker volume create emdash-uploads
emdash-uploads
❯ docker run -d --name emdash -p 4321:4321 -e EMDASH_ENCRYPTION_KEY=emdash_enc_v1_... \
    -v emdash-data:/app/data -v emdash-uploads:/app/uploads emdash
88254b6d6c18065376170dd50289e3b110739f69ccf369048dd64835c9ff4193
```

動きはしますが、この 1 行を毎回打つ人はいません。どこかにメモしておき、コピーして貼ることになります。そしてデータベースを別のコンテナに分けたくなった瞬間、`docker run` が 2 本、ネットワークを作る 1 本、起こす順番の約束、と覚えることが一気に増えます。

それを 1 つの設定ファイルに書いておき、`docker compose up` の 1 コマンドでまとめて動かすのが **Docker Compose** です。今回は、EmDash のリポジトリに同梱されている `compose.yaml` から始めて、前回の `docker run` を置き換え、そこに PostgreSQL を足して 2 つのコンテナを動かします。

この記事は Docker Desktop（Engine 29.8.0、Compose v5.5.1）で確かめています。Compose は Docker Desktop に最初から入っていて、`docker compose` というサブコマンドとして使えます。

## compose.yaml を読む

EmDash のリポジトリの直下に、`compose.yaml` があります。

```yaml title="compose.yaml"
services:
  emdash:
    build: .
    ports:
      - "4321:4321"
    volumes:
      - emdash-data:/app/data
      - emdash-uploads:/app/uploads
    restart: unless-stopped

volumes:
  emdash-data:
  emdash-uploads:
```

`services` の下に並ぶのが、起こすコンテナの設計図です。ここでは `emdash` という名前の**サービス**が 1 つだけあります。前回の `docker run` と並べると、ほとんど 1 対 1 で対応しています。

| `docker run` / `docker volume` | `compose.yaml` |
| --- | --- |
| `docker build -t emdash .` してから `emdash` を起こす | `build: .`（`up` のときにビルドする） |
| `-p 4321:4321` | `ports: ["4321:4321"]` |
| `-e KEY=value` | `environment:` |
| `-v emdash-data:/app/data` | `volumes:`（サービスの下） |
| `docker volume create emdash-data` | `volumes:`（トップレベル） |
| `--restart unless-stopped` | `restart: unless-stopped` |
| `--name emdash` | サービス名 `emdash`（コンテナ名は Compose が付ける。後述） |
| `-d` | `docker compose up -d` |

`restart: unless-stopped` は、前回使わなかったオプションです。コンテナが落ちたときや Docker 自体が再起動したときに、エンジンがコンテナを起こし直してくれます。ただし自分で `stop` したものは起こしません。これが後で効いてきます。

## 起こす

`compose.yaml` のあるディレクトリで `docker compose up -d` を打ちます。`-d` は `docker run -d` と同じで、裏で動かすという意味です。

```console
❯ docker compose up -d
 Image emdash-emdash Building
...
#19 [deps 10/10] RUN pnpm install --frozen-lockfile
#19 CACHED
#20 [build 1/8] COPY . .
#20 DONE 210.3s
...
#23 [build 4/8] RUN pnpm build && pnpm --filter @emdash-cms/template-blog build
#23 DONE 982.7s
#24 [build 5/8] RUN NODE_OPTIONS=--max-old-space-size=4096 pnpm --filter @emdash-cms/template-blog deploy /deploy --prod --legacy
#24 DONE 157.6s
...
 Image emdash-emdash Built
 Network emdash_default Creating
 Volume emdash_emdash-uploads Creating
 Volume emdash_emdash-data Creating
 Volume emdash_emdash-data Created
 Volume emdash_emdash-uploads Created
 Network emdash_default Created
 Container emdash-emdash-1 Creating
 Container emdash-emdash-1 Created
 Container emdash-emdash-1 Starting
 Container emdash-emdash-1 Started
```

`build: .` があるので、まずイメージをビルドしています。中身は前回の `docker build` そのもので、`[deps 10/10]` の `pnpm install` は `CACHED` です。イメージの名前は違っても、ビルドキャッシュは同じエンジンの中で共有されています。それでも `COPY . .` から下はやり直しになり、全体で 27 分半かかりました。

ビルドが終わると、ネットワーク、ボリューム、コンテナの順に作って起こしています。どれも `docker run` のときには自分で名前を付けていたものですが、ここでは Compose が名前を付けています。`docker compose ps` と `docker compose logs` で見ます。

```console
❯ docker compose ps
NAME              IMAGE           COMMAND                   SERVICE   CREATED          STATUS          PORTS
emdash-emdash-1   emdash-emdash   "docker-entrypoint.s…"   emdash    33 seconds ago   Up 29 seconds   0.0.0.0:4321->4321/tcp, [::]:4321->4321/tcp
❯ docker compose logs
emdash-1  | 22:26:18 [@astrojs/node] Server listening on
emdash-1  |   local: http://localhost:4321
emdash-1  |   network: http://172.18.0.2:4321
```

`docker ps` や `docker logs` と同じものですが、`compose.yaml` に書いたサービスだけが対象です。`logs` の各行の頭には、どのサービスの出力かが付きます。サービスが増えたときに、全部のログを 1 か所で見られるのが便利です。

`network:` のアドレスが、前回の `172.17.0.2` から `172.18.0.2` に変わっています。Compose は、プロジェクトごとに専用のネットワーク（`emdash_default`）を作って、そこにコンテナを繋ぐからです。これが後で PostgreSQL を足すときに効いてきます。

### 前回の記事が消えている

では、前回書いた記事を開きます。

```console
❯ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4321/posts/hello-from-a-container
302
❯ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://localhost:4321/_emdash/admin/
302 http://localhost:4321/_emdash/admin/setup
```

記事は無く、管理画面はセットアップウィザードに転送されます。つまり、**まっさらな EmDash** です。前回の記事もアカウントも、`emdash-data` ボリュームの中にあるはずでした。ボリュームの一覧を見ると、理由が分かります。

```console
❯ docker volume ls
DRIVER    VOLUME NAME
local     emdash-data
local     emdash-uploads
local     emdash_emdash-data
local     emdash_emdash-uploads
```

`emdash_emdash-data` という、新しい空のボリュームができています。Compose は、`compose.yaml` に書いた名前の頭に**プロジェクト名**を付けて、ボリュームやネットワークを作ります。プロジェクト名は、既定では `compose.yaml` のあるディレクトリの名前で、ここでは `emdash` です。さっきの出力に並んでいた名前は、全部このルールで説明がつきます。

| もの | `compose.yaml` での名前 | 実際の名前 |
| --- | --- | --- |
| イメージ | `emdash`（サービス） | `emdash-emdash` |
| コンテナ | `emdash`（サービス） | `emdash-emdash-1` |
| ネットワーク | （書いていない） | `emdash_default` |
| ボリューム | `emdash-data` | `emdash_emdash-data` |

プロジェクト名で区切るのは、同じマシンで別々のプロジェクトを動かしたときに、`db` や `data` のようなありふれた名前がぶつからないようにするためです。ありがたい仕組みですが、`docker run` で作った既存のボリュームを使うつもりで書くと、今回のように**黙って空のボリュームを新しく作ります**。エラーも警告も出ません。

### 既存のボリュームを使う

`compose.yaml` の外で作ったボリュームを使うときは、`external: true` を付けます。「これは Compose が作るものではない。この名前のものがすでにある」という宣言です。

```diff title="compose.yaml"
 volumes:
   emdash-data:
+    external: true
   emdash-uploads:
+    external: true
```

いったん `docker compose down` でコンテナを消してから、起こし直します。

```console
❯ docker compose down
 Container emdash-emdash-1 Stopping
 Container emdash-emdash-1 Stopped
 Container emdash-emdash-1 Removing
 Container emdash-emdash-1 Removed
 Network emdash_default Removing
 Network emdash_default Removed
❯ docker compose up -d
time="2026-09-24T07:27:37+09:00" level=warning msg="volume \"emdash_emdash-data\" carries the compose label \"emdash-data\" but does not match the compose file (using \"emdash-data\"); it is left untouched — remove it manually if it is no longer needed"
time="2026-09-24T07:27:37+09:00" level=warning msg="volume \"emdash_emdash-uploads\" carries the compose label \"emdash-uploads\" but does not match the compose file (using \"emdash-uploads\"); it is left untouched — remove it manually if it is no longer needed"
 Network emdash_default Creating
 Network emdash_default Created
 Container emdash-emdash-1 Creating
 Container emdash-emdash-1 Created
 Container emdash-emdash-1 Starting
 Container emdash-emdash-1 Started
❯ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:4321/posts/hello-from-a-container
200
```

今度はビルドが無く、3.3 秒で起きました。イメージはもうあるからです。そして前回の記事が `200` で返ってきます。管理画面も、セットアップではなくログイン画面に転送されるようになりました。

警告は、さっき間違って作った `emdash_emdash-*` の 2 つについてです。「もう `compose.yaml` のどれとも合わないが、触らずに残しておく。要らないなら自分で消してくれ」と言っています。中身は空なので、消します。

```console
❯ docker volume rm emdash_emdash-data emdash_emdash-uploads
emdash_emdash-data
emdash_emdash-uploads
```

> [!TIP]
> 最初から Compose で始めるなら、`external` は要りません。Compose に作らせたボリュームは、Compose が名前を管理してくれます。`external: true` は、`docker run` の時代から使っているボリュームを引き継ぐときや、プロジェクトをまたいで同じボリュームを使うときのためのものです。

## 秘密は .env に置く

前回の `docker run` には `-e EMDASH_ENCRYPTION_KEY=...` がありましたが、同梱の `compose.yaml` にはありません。無くても EmDash は動きますが、プラグインの秘密情報を保存しようとした時点で失敗します。

鍵を作るのに、前回は `docker run --rm emdash ...` でイメージの中の CLI を呼びました。Compose にも同じものがあり、`docker compose run --rm サービス名 コマンド` です。サービスの設定（イメージ、ボリューム、ネットワーク）をそのまま使って、使い捨てのコンテナを 1 つ起こします。

```console
❯ docker compose run --rm emdash node_modules/.bin/emdash secrets generate
 Container emdash-emdash-run-a1715c69eafa Creating
 Container emdash-emdash-run-a1715c69eafa Created
emdash_enc_v1_...

EmDash encryption key generated.

Set EMDASH_ENCRYPTION_KEY in your environment.
For Cloudflare deployments, push it to your Worker's secrets.
For Node deployments, add it to your process environment or .env file.

Keep this value secret. Losing it means losing every secret encrypted with it.
```

この鍵を `compose.yaml` に直接書くと、`compose.yaml` をコミットした瞬間に鍵もリポジトリに入ります。そこで、`compose.yaml` と同じディレクトリに `.env` というファイルを作り、そちらに置きます。

```text title=".env"
EMDASH_ENCRYPTION_KEY=emdash_enc_v1_...
```

`compose.yaml` には、値の代わりに `${変数名}` と書きます。

```yaml title="compose.yaml"
services:
  emdash:
    environment:
      EMDASH_ENCRYPTION_KEY: ${EMDASH_ENCRYPTION_KEY}
```

Compose は、`compose.yaml` を読むときに同じディレクトリの `.env` も読んで、`${...}` を置き換えます。置き換えた結果は `docker compose config` で見られます。

```console
❯ docker compose config
...
    environment:
      EMDASH_ENCRYPTION_KEY: emdash_enc_v1_...
...
```

ここでは伏せましたが、実際には**鍵がそのまま表示されます**。`config` の出力を Issue やチャットに貼るときは気をつけてください。

`up -d` し直すと、Compose は `compose.yaml` が変わったサービスだけを作り直します。

```console
❯ docker compose up -d
 Container emdash-emdash-1 Recreate
 Container emdash-emdash-1 Recreated
 Container emdash-emdash-1 Starting
 Container emdash-emdash-1 Started
```

EmDash のリポジトリの `.gitignore` には、最初から `.env` が入っています。

> [!WARNING]
> `.dockerignore` には `.env` が入っていません。つまり `.env` はビルドコンテキストに入り、`build` ステージの `COPY . .` でイメージの中にコピーされます。最終イメージに `/app/.env` が無いことは確かめました（マルチステージビルドで `build` ステージごと捨てられるからです）が、ビルドキャッシュの中には残ります。自分のプロジェクトでは、`.dockerignore` にも `.env` を書いてください。

## PostgreSQL を足す

ここからが Compose の本領です。EmDash は SQLite で動いていますが、PostgreSQL にも対応しています。データベースを別のコンテナに分けて、2 つのコンテナをまとめて動かします。

まず、EmDash 側の設定を PostgreSQL に切り替えます。ブログのテンプレートの `astro.config.mjs` を、[EmDash のドキュメント](https://docs.emdashcms.com/deployment/database/#postgresql)の例のとおりに書き換えます。

```diff title="templates/blog/astro.config.mjs"
-import { sqlite } from "emdash/db";
+import { postgres } from "emdash/db";
...
-			database: sqlite({ url: "file:./data.db" }),
+			database: postgres({ connectionString: process.env.DATABASE_URL }),
```

`compose.yaml` には、`db` というサービスを足します。イメージは第 1 回で使った `postgres:18-alpine` です。

```yaml title="compose.yaml"
services:
  emdash:
    build: .
    ports:
      - "4321:4321"
    environment:
      EMDASH_ENCRYPTION_KEY: ${EMDASH_ENCRYPTION_KEY}
      DATABASE_URL: postgres://emdash:${POSTGRES_PASSWORD}@db:5432/emdash
    volumes:
      - emdash-uploads:/app/uploads
    depends_on:
      - db
    restart: unless-stopped

  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: emdash
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: emdash
    volumes:
      - pgdata:/var/lib/postgresql

volumes:
  emdash-uploads:
    external: true
  pgdata:
```

ポイントは 3 つです。

- **`DATABASE_URL` のホスト名が `db`** です。Compose が作ったネットワークの中では、**サービス名がそのままホスト名**になります。IP アドレスを調べて書く必要はありません
- `db` には `ports` がありません。PostgreSQL に話しかけるのは同じネットワークの EmDash だけなので、ホストに公開する必要が無いからです
- `depends_on: [db]` で、「`emdash` は `db` の後に起こす」と書いています

PostgreSQL のパスワードも `.env` に 1 行足します。`pgdata` ボリュームは `external` にしていないので、Compose が `emdash_pgdata` という名前で作ります。

設定ファイルを書き換えたので、イメージを作り直します。`up` は、イメージがすでにあればビルドしないので、`--build` を付けます。

```console
❯ docker compose up -d --build
...
#19 [deps 10/10] RUN pnpm install --frozen-lockfile
#19 DONE 215.7s
...
 Image emdash-emdash Built
 Network emdash_default Creating
 Volume emdash_pgdata Creating
 Volume emdash_pgdata Created
 Network emdash_default Created
 Container emdash-db-1 Creating
 Container emdash-db-1 Created
 Container emdash-emdash-1 Creating
 Container emdash-emdash-1 Created
 Container emdash-db-1 Starting
 Container emdash-db-1 Started
 Container emdash-emdash-1 Starting
 Container emdash-emdash-1 Started
❯ docker compose ps
NAME              IMAGE                COMMAND                   SERVICE   CREATED          STATUS          PORTS
emdash-db-1       postgres:18-alpine   "docker-entrypoint.s…"   db        32 seconds ago   Up 30 seconds   5432/tcp
emdash-emdash-1   emdash-emdash        "docker-entrypoint.s…"   emdash    30 seconds ago   Up 29 seconds   0.0.0.0:4321->4321/tcp, [::]:4321->4321/tcp
```

前回の話がそのまま出ています。書き換えた `astro.config.mjs` は `templates/` の下にあり、`deps` ステージが `COPY templates/ templates/` でコピーするファイルです。だから今回は `pnpm install` が `CACHED` にならず、3 分半かけてやり直しました。

`db` が先に、`emdash` が後に起きています。`depends_on` の順番です。`db` の `PORTS` は `5432/tcp` だけで、`->` がありません。ホストには公開されていないということです。

2 つとも `Up` です。ところが、ページを開くと `500` が返ってきます。ここから 2 つの罠を踏みました。

### pg が見つからない

```console
❯ docker compose logs emdash
...
emdash-1  | 22:48:15 [ERROR] Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'pg' imported from /app/dist/server/chunks/dialect_CjqOFQB3.mjs
```

`pg` は、Node から PostgreSQL に繋ぐためのパッケージです。EmDash の依存には入っているので、イメージの中にあるはずです。`docker exec` の Compose 版である `docker compose exec` で、コンテナの中を見ます。コンテナ名ではなく、サービス名で指定します。まず `node_modules` の直下を一覧して `pg` を探すと、こうでした。

```text
@astrojs @emdash-cms astro emdash kysely react react-dom
ls: cannot access 'node_modules/pg': No such file or directory
```

直下には無く、pnpm の置き場所である `node_modules/.pnpm/node_modules/` の奥にはあります。そして直下の `kysely` は、その奥へのリンクでした。

```console
❯ docker compose exec emdash sh -c 'ls -d node_modules/.pnpm/node_modules/pg node_modules/.pnpm/node_modules/kysely; readlink node_modules/kysely'
node_modules/.pnpm/node_modules/kysely
node_modules/.pnpm/node_modules/pg
/app/node_modules/.pnpm/node_modules/kysely
```

Node はビルド済みのサーバーから `pg` を名前で探すので、`node_modules` の直下に無いと見つけられません。前回読んだ `Dockerfile` の実行用ステージには、同じ理由で `kysely` だけをリンクする行がすでにあり、`pg` はそこから漏れていました。SQLite のままなら `pg` を使わないので、誰も気付かなかったわけです。

直し方は、その行に `pg` も足すことです。

```diff title="Dockerfile"
 RUN mkdir -p data uploads \
-    && ln -s /app/node_modules/.pnpm/node_modules/kysely /app/node_modules/kysely
+    && ln -s /app/node_modules/.pnpm/node_modules/kysely /app/node_modules/kysely \
+    && ln -s /app/node_modules/.pnpm/node_modules/pg /app/node_modules/pg
```

この修正は [PR #3406](https://github.com/emdash-cms/emdash/pull/3406) として送ってあります。レビューで、libSQL 用のドライバーも同じ理由で見つからないと指摘されたので、PR ではそちらのリンクも足しています。

> [!NOTE]
> 先に `docker compose exec emdash ln -s ...` でコンテナの中に直接リンクを作って試しましたが、次に `compose.yaml` を変えて `up -d` したとき、コンテナが作り直されてリンクは消えました。コンテナの中で直したものは、書き込み層と一緒に消えます。第 1 回でやったことの、そのままの再現です。直すならイメージ（`Dockerfile`）です。

### DATABASE_URL が読まれない

`pg` が見つかると、今度はこうなりました。

```console
❯ docker compose logs emdash
...
emdash-1  | 22:49:26 [ERROR] Error: connect ECONNREFUSED 127.0.0.1:5432
```

`127.0.0.1` は、コンテナ自身です。`DATABASE_URL` に `db` と書いたのに、そこを見ていません。環境変数はちゃんと入っています（パスワードは `sed` で伏せています）。

```console
❯ docker compose exec emdash sh -c 'printenv DATABASE_URL | sed "s#//emdash:[^@]*@#//emdash:***@#"'
postgres://emdash:***@db:5432/emdash
```

原因は、ビルドしたサーバーの中にありました。

```console
❯ docker compose exec emdash sh -c 'grep -n -A8 "\"database\": {" dist/server/chunks/config_B4S-UmlO.mjs'
3:	"database": {
4-		"entrypoint": "emdash/db/postgres",
5-		"config": {},
6-		"type": "postgres",
...
```

`"config": {}` です。`astro.config.mjs` の `process.env.DATABASE_URL` は、コンテナを起こしたときではなく、**イメージをビルドしたときに**評価されて、その結果がサーバーに焼き込まれます。ビルド中の `DATABASE_URL` は空なので、焼き込まれた設定も空です。コンテナに何を渡しても読まれません。

設定が空のとき、`pg` は `PGHOST`、`PGUSER`、`PGPASSWORD`、`PGDATABASE` という環境変数を見に行きます（PostgreSQL のクライアントに共通の決まりです）。こちらは実行時に読まれるので、`compose.yaml` の環境変数をそちらに書き換えれば、ビルドし直さずに済みます。

```diff title="compose.yaml"
     environment:
       EMDASH_ENCRYPTION_KEY: ${EMDASH_ENCRYPTION_KEY}
-      DATABASE_URL: postgres://emdash:${POSTGRES_PASSWORD}@db:5432/emdash
+      PGHOST: db
+      PGUSER: emdash
+      PGPASSWORD: ${POSTGRES_PASSWORD}
```

`depends_on` が待つのは、`db` の**コンテナが起動するまで**です。PostgreSQL が接続を受け付けるようになるまでではありません。空のボリュームから起こした PostgreSQL は、最初にデータベースを作る初期化に 5 秒ほどかかります。そのあいだに来たリクエストで EmDash は接続に失敗し、「直前に失敗したので少し待つ」状態に入りました。そこから `backing off` のエラーを 28 回出し、PostgreSQL の準備ができてから 34 秒後に、やっとデータベースを使い始めています。

しかもこのあいだ、`curl` で見た管理画面のステータスコードは `200` でした（正常なら、セットアップへの `302` です）。ステータスコードだけを見ていると、壊れていることに気付けません。

「コンテナが起動した」ではなく「使える状態になった」まで待たせるのが、**healthcheck** です。`db` に「使える状態かどうか」を確かめるコマンドを持たせ、`emdash` の `depends_on` で「`db` が healthy になってから起こす」と書きます。

```diff title="compose.yaml"
     depends_on:
-      - db
+      db:
+        condition: service_healthy
     restart: unless-stopped

   db:
     image: postgres:18-alpine
     ...
+    healthcheck:
+      test: ["CMD", "pg_isready", "-U", "emdash"]
+      interval: 2s
+      retries: 15
```

`pg_isready` は PostgreSQL に付いてくるコマンドで、接続を受け付けているかどうかだけを確かめます。それを 2 秒ごとに、15 回まで試します。もう一度データベースを空にして起こします。今度は `down` でコンテナを消してから、`down -v` で残ったボリュームを消しました（`down -v` はコンテナが無くても、ボリュームだけを消します）。

最後に、`restart: unless-stopped` の話です。同梱の `compose.yaml` では `emdash` にだけ付いていて、足した `db` には付けていませんでした。

## 実際に踏んだ罠

### EmDash の stop は、毎回強制終了になる

`docker compose stop` の後で `ps -a` を見ると、終了コードが `137` になっていました。PostgreSQL を足す前、EmDash だけを動かしていたときの記録です。

```console
❯ docker compose stop
 Container emdash-emdash-1 Stopping
 Container emdash-emdash-1 Stopped
❯ docker compose ps -a
NAME              IMAGE           COMMAND                   SERVICE   CREATED          STATUS                      PORTS
emdash-emdash-1   emdash-emdash   "docker-entrypoint.s…"   emdash    19 seconds ago   Exited (137) 1 second ago
```

`137` は 128 + 9 で、`SIGKILL`（強制終了）で殺されたという意味です。`stop` はまず `SIGTERM`（終了してください、というお願い）を送り、それで終わらなければ `SIGKILL` を送ります。試しに `docker kill -s TERM emdash-emdash-1` で `SIGTERM` だけを送り、コンテナが止まるまでを測りました。

```console
❯ s=$(date +%s%N); docker kill -s TERM emdash-emdash-1 >/dev/null; until [ "$(docker inspect emdash-emdash-1 --format '{{.State.Running}}')" = false ]; do sleep 0.2; done; echo "SIGTERM -> exit after $(( ($(date +%s%N)-s)/1000000 )) ms, code $(docker inspect emdash-emdash-1 --format '{{.State.ExitCode}}')"
SIGTERM -> exit after 74503 ms, code 137
```

74 秒経っても止まらず、止まったのは、こちらが改めて `docker stop` したときでした。終了コードも `137` です。

ログの `(node:1)` が示すとおり、コンテナの中では Node が PID 1 で動いています。Linux では PID 1 のプロセスに届いたシグナルは、そのプロセスが自分で処理を書いていない限り無視されます。対照的に PostgreSQL は、`SIGTERM` を受けて `received fast shutdown request` とログに残し、きれいに止まっていました。

EmDash の場合、止まって困るのは書きかけのリクエストくらいで、データは PostgreSQL 側にあります。ただ、自分のアプリで同じことが起きていたら、`stop` のたびに後始末の処理が飛ばされていることになります。Compose には、PID 1 に小さな init プロセスを置く `init: true` という設定がありますが、この記事では試していません。

### Git Bash がパスを書き換える

[第 1 回](/ja/blog/getting-started-with-docker#git-bash-がパスを書き換える)で書いた罠を、`docker compose exec` でも踏みました。

```console
❯ docker compose exec emdash ln -s /app/node_modules/.pnpm/node_modules/pg /app/node_modules/pg
ln: failed to create symbolic link 'C:/Program Files/Git/app/node_modules/pg': No such file or directory
```

`docker compose` になっても、引数を書き換えているのは Git Bash なので、同じく `MSYS_NO_PATHCONV=1` で止まります。

| --- | --- |
| `docker compose up -d` | 足りないものを作って、全部のサービスを裏で起こす。変わったサービスだけ作り直す |
| `docker compose up -d --build` | イメージをビルドし直してから起こす |
| `docker compose ps` / `ps -a` | このプロジェクトのコンテナの一覧 / 止まったものも含めて |
| `docker compose logs` / `logs -f SERVICE` | 全サービスのログ / そのサービスのログを追いかける |
| `docker compose exec SERVICE CMD` | 動いているサービスのコンテナでコマンドを実行する |
| `docker compose run --rm SERVICE CMD` | サービスの設定で使い捨てのコンテナを起こして CMD を実行する |
| `docker compose stop` / `start` | 止める / 起こし直す（コンテナは残る） |
| `docker compose down` | コンテナとネットワークを消す（ボリュームは残る） |
| `docker compose down -v` | ボリュームも消す（`external` のものは残る） |
| `docker compose config` | `.env` を読み込んで置き換えた後の設定を表示する（秘密も表示される） |

## まとめ

- Docker Compose は、`docker run` の長い 1 行とボリュームやネットワークの準備を `compose.yaml` に書き下ろして、`docker compose up` でまとめて動かすもの
- Compose は名前の頭に**プロジェクト名**を付ける。`docker run` で作った既存のボリュームを使うなら `external: true`。書き忘れると、黙って空のボリュームができる
- 秘密は `.env` に置いて `${VAR}` で参照する。`.gitignore` と `.dockerignore` の両方に `.env` を書く
- サービス名がそのままホスト名になる。データベースは `ports` で公開しなくても、同じプロジェクトのコンテナからは繋がる
- `depends_on` が待つのはコンテナの起動まで。「使える」まで待たせるには healthcheck と `condition: service_healthy`
- `down` はデータを残し、`down -v` はデータごと消す
- `restart` で起こし直すのはエンジンで、`depends_on` の順番は守られない
- `astro.config.mjs` の `process.env` はビルドのときに焼き込まれる。コンテナに渡す環境変数が効くとは限らない

前回と今回で、EmDash の公式の `Dockerfile` に 2 本の PR を送ることになりました。どれも、誰かが実際にその構成でビルドして動かすまで、表に出なかった壊れ方です。動かない公式の設定を見つけたら、ログを読んで、どのコンテナから何が見えていないのかを辿れば、たいてい直せます。
